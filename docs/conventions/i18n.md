# Internationalization (i18n)

> **Hard rule:** No hardcoded user-facing strings. All user-facing text
> passes through i18n catalogs (next-intl on the frontend, Laravel
> `lang/` on the backend). ESLint enforces this on JSX.

Azimuth ships bilingual from day one. The discipline below is the cost
of that choice; the upside is that adding a third language is a
catalog-only change and the canonical key for any string is always the
same place.

## Stack

- **Frontend:** [next-intl](https://next-intl.dev) with the App Router
  `[locale]` segment pattern. Server Components use
  `getTranslations`; Client Components use the `useTranslations` /
  `useLocale` hooks.
- **Backend:** Laravel 13 native `lang/` files (validation messages,
  mail, command output) plus
  [spatie/laravel-translatable](https://github.com/spatie/laravel-translatable)
  on Eloquent models for content fields that need per-locale storage.
- **Shared:** `libs/i18n/` exposes `LOCALES`, `DEFAULT_LOCALE`, the
  `Locale` type, the `isLocale` type guard, and the
  monorepo-wide message bundle. Both the Next.js `request.ts` and the
  middleware import from `@azimuth/i18n` so there is exactly one
  source of truth for "which locales does Azimuth support?".

## Locales

Defined in [`libs/i18n/src/locales.ts`](../../libs/i18n/src/locales.ts):

```ts
export const LOCALES = ['en', 'pt'] as const;
export type Locale = (typeof LOCALES)[number];
export const DEFAULT_LOCALE: Locale = 'en';
```

To add a locale, see [`../runbooks/adding-a-locale.md`](../runbooks/adding-a-locale.md).
The short version: extend `LOCALES`, mirror every catalog file, then
re-run the typegen so consumers see the new union.

## Where catalogs live

| Surface                         | Path                                            | Format             |
| ------------------------------- | ----------------------------------------------- | ------------------ |
| Shared frontend strings         | `libs/i18n/src/messages/<locale>.json`          | next-intl JSON     |
| Per-feature frontend strings    | `apps/web/src/messages/<scope>.<locale>.json`   | next-intl JSON     |
| Backend validation / mail / cli | `apps/backend/lang/<locale>/<file>.php`         | Laravel PHP arrays |
| Eloquent translatable fields    | `<table>.<column>` (per-locale JSON via Spatie) | Database           |

Two layers on the frontend on purpose:

- **Shared** (`libs/i18n/src/messages/`) holds chrome that every page
  uses — `common`, `nav`, `theme`, `locale`. These ship in every
  bundle.
- **Per-feature** (`apps/web/src/messages/<scope>.<locale>.json`) holds
  scope-specific keys like `auth.loginTitle`. The Next.js
  `request.ts` merges them at render time so the
  `useTranslations('auth')` hook just works without manual wiring at
  the page level.

The merge happens in [`apps/web/src/i18n/request.ts`](../../apps/web/src/i18n/request.ts).
Adding a new feature scope means adding the import there too.

## Frontend: adding a key

1. **Decide which catalog the key belongs to.** Generic chrome →
   `libs/i18n/src/messages/en.json`. Feature-specific →
   `apps/web/src/messages/<scope>.en.json`. When in doubt, prefer the
   feature catalog; lifting a key into shared is cheap, demoting one
   later is annoying.
2. **Add the key under its scope** (always nested under the scope name
   so `useTranslations('scope')` resolves it):

   ```json
   {
     "auth": {
       "loginTitle": "Sign in to Azimuth"
     }
   }
   ```

3. **Mirror the key in every other locale catalog.** CI does not yet
   enforce drift between locales — it is on reviewer judgment to
   reject PRs that add `en` but forget `pt`. (Drift detection is
   tracked for Phase 5.)
4. **Use the key.** In a Server Component:

   ```tsx
   import { getTranslations } from 'next-intl/server';

   export default async function Page() {
     const t = await getTranslations('auth');
     return <h1>{t('loginTitle')}</h1>;
   }
   ```

   In a Client Component:

   ```tsx
   'use client';
   import { useTranslations } from 'next-intl';

   export function LoginButton() {
     const t = useTranslations('auth');
     return <button>{t('continueWithStub')}</button>;
   }
   ```

5. **Locale-aware links** keep the active locale in the URL — see
   `apps/web/src/app/[locale]/login/page.tsx` for the canonical
   pattern: read `useLocale()` and template it into the `href`.

## ESLint enforcement

The hardcoded-string ban is enforced at lint time in
[`apps/web/eslint.config.mjs`](../../apps/web/eslint.config.mjs) via
`react/jsx-no-literals` with `noStrings: true`. JSX text nodes that
are not the result of a translation call are an error, not a warning:

```js
'react/jsx-no-literals': [
  'error',
  {
    noStrings: true,
    ignoreProps: true,
    allowedStrings: ['—', '·', '▾', ':', '/', '|', '×'],
    noAttributeStrings: false,
  },
],
```

The `allowedStrings` list covers visual punctuation and separators
that are not user-facing copy. Add to it sparingly; a new entry is a
review-board decision, not a one-line change.

## Plurals and formatting

next-intl uses [ICU MessageFormat](https://formatjs.io/docs/core-concepts/icu-syntax/),
so plurals, selects, and rich values all live inside the catalog
string. Keep the logic in the message, not the component.

```json
{
  "ping": {
    "items": "{count, plural, =0 {No pings} one {# ping} other {# pings}}"
  }
}
```

```tsx
const t = useTranslations('ping');
return <p>{t('items', { count: pings.length })}</p>;
```

For dates and numbers, use `useFormatter` so the locale picks the
right separator, calendar, and currency formatting:

```tsx
const f = useFormatter();
f.dateTime(date, { dateStyle: 'long' });
f.number(value, { style: 'currency', currency: 'USD' });
```

Never hand-roll `Intl.NumberFormat` or string-concat dates — the
formatter is locale-aware, your concatenation is not.

## Backend: adding a key

1. Add the key to `apps/backend/lang/en/<file>.php`. The file returns
   a PHP array, nested as deeply as you like:

   ```php
   <?php

   declare(strict_types=1);

   return [
       'navigation' => [
           'group' => 'Modules',
           'label' => 'Pings',
       ],
   ];
   ```

2. Mirror the key in every other locale (`apps/backend/lang/pt/<file>.php`,
   etc.). Reviewer judgment for now; CI drift detection is Phase 5.
3. Read the key with the global helpers:

   ```php
   __('ping.navigation.label');                    // 'Pings'
   trans('ping.note.locale_label');                // 'Locale'
   trans('ping.fields.user', ['name' => $user]);   // with placeholders
   ```

4. Validation messages live in `lang/<locale>/validation.php` (Laravel
   convention). Override per-attribute messages there rather than
   inline in the FormRequest.
5. The active locale comes from `App::setLocale($locale)` — middleware
   sets this from the `?locale=` query param when an HTTP call
   originates from the locale-aware frontend.

## Locale negotiation

- The browser sends `Accept-Language`.
- [`apps/web/src/middleware.ts`](../../apps/web/src/middleware.ts)
  uses `next-intl/middleware` with `localePrefix: 'always'` to pick
  the closest match from `LOCALES`, falling back to `DEFAULT_LOCALE`
  (`en`).
- The matched locale is prepended to every URL, e.g. `/en/dashboard`
  or `/pt/login`. This makes the active locale explicit, shareable,
  and cacheable per-locale.
- API routes are excluded from the middleware matcher
  (`/((?!api|_next|_vercel|favicon.ico).*)`); they receive locale
  intent via the `?locale=` query param when triggered from
  locale-aware UI. See the stub-callback flow in `login/page.tsx` for
  the canonical example.

## Translatable database fields

For Eloquent columns whose value is itself user-facing copy (a
description, a label, a marketing blurb), use Spatie's translatable
trait so each row holds a per-locale JSON map.

Migration:

```php
$table->json('description');
```

Model:

```php
use Spatie\Translatable\HasTranslations;

class Aircraft extends Model
{
    use HasTranslations;

    public array $translatable = ['description'];
}
```

Reading and writing:

```php
$aircraft->description;                                 // current locale
$aircraft->getTranslation('description', 'pt');         // explicit
$aircraft->setTranslation('description', 'pt', 'Caça'); // write
```

Spatie serializes per-locale JSON on save. Don't reach for a separate
`translations` table — the trait is enough for every translatable
field Azimuth has needed so far.

## What NOT to translate

Some strings are identifiers, not copy. They never go through the
catalog system:

- **ULIDs and UUIDs.** Identifiers, not text.
- **Enum `value` keys.** Each `BackedEnum` case has a stable
  machine-readable `value`; that is the canonical reference (e.g. the
  `Permission` enum's `value` is what authorization checks against).
  The translatable surface is the enum's `label()` method, which
  returns `__('module.permissions.<value>')`.
- **API field names** in JSON responses. The shape of the wire format
  is a contract with `libs/api-client` — translate the human label,
  not the field key.
- **Log messages, exception messages, command output.** These are
  developer-facing diagnostics, not user copy. Keeping them in English
  makes triage faster.
- **Database column names.** Same logic as enum values — the
  canonical reference is stable, the human label is derived.

When in doubt: if a designer would write copy for it, it goes through
i18n. If only an engineer would ever read it, it stays in English.
